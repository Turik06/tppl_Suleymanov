1. Что такое ассемблер и WebAssembly

Классический ассемблер

Низкоуровневый язык команд конкретного процессора (x86, ARM). Прямая работа с физическими регистрами CPU и памятью компьютера.

WebAssembly — «Виртуальный ассемблер»

Переносимый бинарный машинный код для абстрактной виртуальной машины. Независим от железа, выполняется везде с защитой памяти.

Название: Web + Assembly

Web — безопасность и работа в любых браузерах. Assembly — машинный байткод с околонативной скоростью (~95% C++).

Пункт 1: Что такое ассемблер и WebAssembly, конвейер компиляции. - Классический ассемблер: мнемоники конкретного процессора (x86, ARM), аппаратные регистры (EAX, R0), прямая память. Код x86 не запустится на ARM. - WebAssembly: «виртуальный ассемблер». Бинарный код для абстрактной виртуальной машины. Платформенно-независим и аппаратно изолирован. - Web + Assembly: Web — безопасность исполнения в среде хоста; Assembly — скорость (~95% от нативного Си). Это таргет компиляции системных языков. Конвейер на примере 3D-игры (Doom 3 / Unity): 1. Исходник: физика и матрицы на C/C++/Rust. На JS писать нельзя — GC периодически замораживает поток на десятки мс. 2. Сборка: Clang с флагом --target=wasm32 транслирует код в опкоды Wasm. 3. Модуль math.wasm: всего 62 байта чистых инструкций. 4. Сеть: скачивается по HTTPS за доли секунды. 5. Рантайм: движок (V8, WebKit, Node.js) через JIT компилирует байткод под CPU пользователя. 6. Аппаратный CPU: прямое выполнение на 4 ГГц с 95% скорости Си (5% — цена проверки границ памяти).

1.1. Почему провалились предшественники (1995–2013)

NPAPI-плагины: Flash, Java Applets, ActiveX

  • Причина провала: отсутствие изоляции памяти, прямой доступ к ресурсам ОС, частые уязвимости безопасности.
  • Отказ мобильных платформ: письмо Стива Джобса «Мысли о Flash» (2010) из-за сбоев и жора батареи. Закрыт в 2020 г.

Google Native Client (NaCl / PNaCl, 2011)

  • Причина провала: проприетарная закрытость Google и привязка к x86. Другие вендоры (Mozilla, Apple) отказались внедрять монополию.

Перерождение: asm.js (Mozilla, 2013) ➔ Wasm

  • Компиляция C++ в строгое подмножество JS. Доказал идею, но уперся в парсинг 100-МБ текстовых файлов JS. Переродился в Wasm!

Flash Player (1996–2020): закрыт из-за проблем безопасности

Причины провала предшественников: 1. NPAPI-плагины (Flash, ActiveX): внешние процессы с прямым доступом к Win32 API и физической памяти. Итог: постоянные критические уязвимости и краши браузеров. В 2010 г. Стив Джобс в письме «Мысли о Flash» запретил Flash на iPhone из-за дыр безопасности и пожирания батареи. В 2020 г. Flash был закрыт. 2. Google Native Client (NaCl, 2011 г.): давал нативную скорость, но провалился из-за монополии Google и жесткой привязки к x86. Apple и Mozilla отказались внедрять закрытый стандарт конкурента. 3. asm.js (Mozilla, 2013 г.): доказал компиляцию C++ в подмножество JS ((a+b)|0), но уперся в парсинг текстового JS: файлы по 100 МБ вешали движки браузера. Вывод: индустрии требовался открытый бинарный стандарт от всех вендоров сразу.

1.2. Рождение стандарта WebAssembly (2015–2019)

2015: Альянс 4 гигантов

Google (Chrome), Mozilla (Firefox), Apple (Safari) и Microsoft (Edge) впервые в истории объединились ради создания единого открытого стандарта после 20 лет браузерных войн.

2017: Согласованный MVP

Все 4 основных браузерных движка одновременно включили поддержку WebAssembly по умолчанию без необходимости активации флагов.

2019: Официальный стандарт W3C

Консорциум W3C официально утвердил WebAssembly в статусе 4-го языка веба — наряду с HTML, CSS и JavaScript.

Ключевой итог эволюции: Отказавшись от проприетарных плагинов и текстовых хаков, индустрия создала открытый бинарный формат с детерминированным исполнением и защитой памяти на уровне команд виртуальной машины.
Рождение стандарта WebAssembly: 1. 2015: Альянс 4 гигантов. Google, Mozilla, Apple и Microsoft объединились в W3C ради единого открытого стандарта после 20 лет браузерных войн. 2. 2017: Согласованный релиз MVP. Все 4 движка одновременно включили Wasm по умолчанию без флагов. 3. 2019: Официальный стандарт W3C. WebAssembly утвержден 4-м языком веба (наряду с HTML, CSS и JavaScript). Итог: открытый бинарный байткод с изоляцией на уровне инструкций виртуальной машины.

3. Управление памятью и типизация

Линейная память (Linear Memory)

Один непрерывный массив байт (ArrayBuffer). Изолирован от ОС. Попытка выхода за пределы вызывает аппаратный Trap.

Управление памятью: Без GC

В ядре базового Wasm нет сборщика мусора! Управление ручное: в C через malloc/free, в Rust через borrow-checker.

Всего 4 числовых типа

Строгая статическая типизация: i32, i64, f32, f64. Нет встроенных типов строк или объектов (только сырые байты).

Управление памятью и типизация (3 принципа): 1. Линейная память: сплошной байтовый массив (ArrayBuffer). Модуль изолирован от памяти ОС. При выходе за границы выделенного массива виртуальная машина вызывает аппаратный сбой (Trap), браузер не падает. 2. Без сборщика мусора (No GC): памятью управляет сам язык (malloc/free в Си, borrow checker в Rust). Нет пауз на сборку мусора — скорость предсказуема и стабильна. 3. Строго 4 числовых типа: i32, i64, f32, f64. Строк и объектов нет — текст передается парой чисел: смещение в памяти и длина в байтах.

3.1. Архитектурные особенности виртуальной машины

1. Стековая машина (Без регистров)

В отличие от процессоров x86/ARM, в виртуальной машине Wasm нет регистров общего назначения. Все команды оперируют вершиной стека (LIFO):

local.get $a  ;; положить 'a' в стек
local.get $b  ;; положить 'b' в стек
i32.add       ;; сложить: забрать a, b -> положить (a + b)

2. Принцип «Слеп и глух»

Модуль тотально изолирован: он не имеет прямого доступа ни к экрану, ни к DOM, ни к диску или сети. Взаимодействие возможно только через явные функции-импорты хоста (Capability-based).

3. Двойственный формат (.wasm / .wat)

.wasm — бинарный компактный байткод для машин.

.wat — текстовый человекочитаемый формат на S-выражениях (Lisp-синтаксис) для отладки и дизассемблирования.

Архитектурные особенности виртуальной машины: 1. Стековая машина (LIFO): нет регистров. Инструкции local.get $a и local.get $b кладут операнды на вершину стопки, i32.add забирает их и кладет сумму. Каждая команда занимает всего 1 байт — файл получается максимально компактным. 2. Изоляция «слеп и глух»: модуль не имеет прямого доступа к DOM, диску или сети. Взаимодействие только через функции-импорты, явно переданные хостом (Capability-based). 3. Двойной формат: .wasm — сжатый бинарный байткод для машины; .wat — читаемый текст на S-выражениях для человека.

4. Пример использования и компиляция

1. Исходник на языке C (math.c)

// Рекурсивное вычисление факториала
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

2. Команда сборки через Clang / LLVM

# Сборка через LLVM/Clang в 32-битный Wasm
clang --target=wasm32 -O3 -nostdlib \
  -Wl,--no-entry -Wl,--export-all \
  -o math.wasm math.c

3. Байткод в текстовом формате WAT (math.wat)

(module
  (func $factorial (param $n i32) (result i32)
    local.get $n      ;; положить n в стек
    i32.const 1       ;; положить 1 в стек
    i32.le_s          ;; проверка: n <= 1 ?
    if (result i32)   ;; если да (базовый случай):
      i32.const 1     ;;   вернуть 1
    else              ;; иначе (рекурсия):
      local.get $n    ;;   положить n
      local.get $n    ;;   положить n
      i32.const 1     ;;   положить 1
      i32.sub         ;;   вычесть (n - 1)
      call $factorial ;;   рекурсивный вызов
      i32.mul         ;;   умножить n * fact(n-1)
    end)
  (export "factorial" (func $factorial)))
Пункт 4: Пример использования и компиляция. 1. Исходник math.c: рекурсивный факториал (n <= 1 -> 1, иначе n * fact(n-1)). 2. Разбор флагов Clang: - target=wasm32: генерация 32-битного байткода Wasm. - O3: максимальная оптимизация. - nostdlib: отключение libc (исключает лишний код). - Wl,--no-entry: сборка библиотеки без main(). - Wl,--export-all: экспорт функции наружу для вызова из JS. Результат: готовый модуль весит всего 62 байта! 3. Байткод WAT: наглядно видна стековая логика — local.get $n, i32.const 1, сравнение i32.le_s, ветвление if...else, вычитание i32.sub, рекурсивный call, перемножение i32.mul.

5. Перспективы развития стандартов

1. WASI 0.2 (Preview 2)

Стандартизированный POSIX-подобный системный слой с моделью Capability-based Security: модуль физически изолирован и получает доступ только к явно выданным файлам и сокетам.

2. Component Model & WIT

Бесшовная интеграция языков: модуль на Rust напрямую взаимодействует с кодом на Go или Python без написания сложного C FFI.

3. Спецификация Wasm GC

Финализирована в 2023–2024 гг. Дает языкам со сборщиком мусора (Dart, Kotlin, Java) нативный доступ к GC браузера. (Пример: Flutter Web на Wasm стал работать в 2–3 раза плавнее!).

4. Векторизация SIMD и Потоки

128-битные инструкции и многопоточность на всех ядрах CPU для локального инференса нейросетей прямо на устройстве пользователя.

Пункт 5: Перспективы развития стандартов: 1. WASI 0.2: серверный запуск со строгой выдачей прав (только разрешенные папки и сокеты). 2. Component Model: прямое взаимодействие модулей на Rust, Go, Python без написания C FFI. 3. Wasm GC: нативный доступ к сборщику мусора браузера для языков со сборщиком (Dart, Kotlin, Java). Flutter Web стал в 2–3 раза плавнее. 4. SIMD и потоки: 128-битные векторные инструкции и параллелизм для локальных нейросетей на процессоре клиента.

6. Альтернативы по областям применения

Область: Клиентский веб

Wasm vs JavaScript

  • Контекст: логика и вычисления в браузере.
  • JavaScript: динамический, GC (паузы), лучший выбор для UI, кнопок и работы с DOM.
  • WebAssembly: статический, без GC, ~95% скорости C++ для 3D, физики и видео.
  • Итог: Симбиоз (JS для интерфейса, Wasm для вычислений).
Область: Облака и Serverless

Wasm (WASI) vs Docker

  • Контекст: запуск микросервисов по клику.
  • Docker: тащит ОС Linux (100–500 МБ), старт 200–500 мс (namespaces ядра).
  • WebAssembly: чистый бинарник (килобайты), старт < 1 мс (микросекунды).
  • Итог: Конкуренция в бессерверных и Edge-средах.
Область: Переносимый байткод

Wasm vs JVM (Java)

  • Контекст: Концепция «Написано однажды — работает везде».
  • JVM: жестко навязала объектную модель Java, байткод JVM и встроенный GC.
  • WebAssembly: нейтрален к языкам (C, Rust, Go), ручное управление памятью.
  • Итог: Альтернатива традиционным объектным VM.
Вывод по альтернативам: WebAssembly сравнивается в разных плоскостях: в браузере он дополняет JavaScript, на сервере выигрывает у Docker по скорости старта, а в переносимости предлагает независимость от Java.
Пункт 6: Альтернативы по областям применения: 1. В браузере (Wasm vs JS): симбиоз. JS для DOM и интерфейса, Wasm для тяжелых вычислений и графики. 2. В облаках (Wasm vs Docker): прямая конкуренция в Serverless. Docker тащит 300 МБ Linux и стартует сотни мс; Wasm весит килобайты и стартует за доли мс. 3. В переносимом байткоде (Wasm vs JVM): концепция «Написано однажды — работает везде». JVM навязала Java и свой GC. Wasm нейтрален и исполняет C, Rust, Go без привязки к ООП. Итог: Wasm дополняет JS, конкурирует с Docker и предлагает независимую альтернативу JVM.
